# Snip capture measurements — 2026-10-13

## Setup and method

- **Machine:** Apple M4, 16 GiB unified memory, macOS 27.0.1.
- **Display:** built-in display, 2940 × 1912 physical pixels; 1470 × 956 scaled mode at 60 Hz.
- **Snip settings in both samples:** 120 FPS selected; Retina resolution; 16 Mbps HEVC target; 30-second clip length; 1024 MB rolling buffer cap; system audio enabled; all apps included for video and audio; neutral color settings.
- **Workload:** Snip running on a stationary desktop. ScreenCaptureKit capture start was observed in the system log for the second sample. Each run sampled one process every 0.5 seconds for 30 seconds with `ps`; CPU percentage is per logical CPU (100% = one logical CPU). RSS is resident process memory, not total system capture service memory. Raw readings, time, OS, display, and settings are in the JSON files below.
- **Build difference:** The second build uses the selected display's `maximumFramesPerSecond` to cap ScreenCaptureKit's requested frame interval and the encoder's expected frame rate. On this display, a selected 120 FPS resolves to 60 FPS. The settings panel now explains that cap.

| Metric | Before cap | After cap |
| --- | ---: | ---: |
| CPU median | 21.0% | 5.1% |
| CPU 95th percentile | 27.62% | 5.71% |
| CPU maximum | 29.0% | 6.2% |
| RSS median | 151.41 MiB | 134.36 MiB |
| RSS 95th percentile | 151.69 MiB | 134.47 MiB |
| RSS maximum | 151.75 MiB | 134.50 MiB |

The median CPU reading was 75.7% lower in the second observation; median RSS was 11.3% lower. This is an observational comparison from one run per build. Desktop activity, capture content, process history, and OS scheduling were not held constant, so those percentages are **not** a causal performance claim. The important code change is that Snip no longer asks a 60 Hz display for 120 FPS. Neither sample approached the 1024 MB configured buffer limit in process RSS, but RSS does not prove a hard total memory ceiling.

## Output quality check

`ffprobe` inspected an existing Snip clip saved with the first build. It reported **2940 × 1912 pixels**, HEVC Main, `yuv420p`, AAC audio at 48 kHz, and nominal 60 FPS. The video pixel dimensions match the display's physical Retina dimensions, rather than its 1470 × 956 logical mode. The short 1.827-second clip contained 75 video frames; the median and 95th percentile gap between decoded frame timestamps were both 16.67 ms. Its 4.7 Mbps whole-file bitrate is below the 16 Mbps target because actual bitrate depends on scene content and encoder behavior.

This clip does not establish perceptual fidelity: there was no lossless reference for PSNR or SSIM. It was too short to prove a full 30-second buffer or sustained frame pacing in a game. ScreenCaptureKit can omit repeated still frames, so a long gap in frame timestamps during a stationary desktop should not automatically be read as dropped gameplay frames. The sample video was not committed to the repository; only its metadata is in the JSON.

## Reproduce

With Snip installed at `/Applications/Snip.app`, recording permission granted, and the desired settings applied:

```sh
python3 scripts/benchmark.py sample --label run-name --seconds 30 --interval 0.5 --output benchmarks/raw/run-name.json
```

To add saved-clip metadata, install `ffprobe` and run:

```sh
python3 scripts/benchmark.py inspect --output benchmarks/raw/run-name.json --clip /path/to/clip.mov
```

Inspect the `cpu_percent`, `rss_mib`, `settings`, `system`, and `samples` fields. Confirm recording is active during the sample; a permission prompt or paused state can otherwise produce misleadingly low CPU readings.
